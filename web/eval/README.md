# 経過簿の読み取りの検証（書式の違い・写真・PDF・Excel）

蔵ごとに書式が違う経過簿を、取り込み画面と同じ処理（`src/read-pipeline.js` と `shared/sheet-map.mjs`）で読み、正解と比べた。

## 試した書式（6種類）

| 書式 | 中身 |
|---|---|
| 標準 | 用紙どおり。日付が横、項目が縦（月日・日順・時刻・操作・品温・ボーメ・日本酒度・アルコール分・酸度・状ぼう・備考） |
| 日付が縦に並ぶ | 1行＝1日。見出しが横に並ぶ |
| 項目名が違う | 日付・醪日数・温度・BMD・SMV・アル分・酸・泡・メモ |
| 項目の順番が違う | 品温・月日・状ぼう・日本酒度・日順…と入れ替えた順 |
| 一部の項目が無い | 月日・日順・品温・日本酒度・状ぼう だけ |
| 複数のタンクを1枚に | 1行＝1つのタンクの1日。タンクの列あり（1・2・4号を4日分） |

それぞれを次の形で用意した（`sheets/`。値はすべて架空のデモデータ `public/data/season-current.json` から作り、正解は `sheets/truth.json`）。

- **手書き風の写真**：手書き風の書体（Klee One・Yomogi・Zen Kurenaido）で、字ごとに傾き・揺れ・濃さのむらを付け、机の上で少し傾けて撮った見た目
- **悪条件の写真**：字の揺れを大きくし、暗く、斜めから、ぶれて、画素の少ない（長い辺 1400px・JPEG の画質も低い）写真
- **限界の写真**（2回目から）：さらにぶれて暗く、長い辺 1000px。見出しも人が読むのに苦労するくらい。読めない欄が誤りでなく「要確認」になるかを見る
- **スキャンした PDF**：同じ用紙をスキャナで取った見た目の PDF（画像の PDF）
- **Excel**：同じ表を Excel にしたもの（日付は Excel の日付、日本酒度のマイナスは数値）

## 数え方

- 正解のある欄（空欄でない欄）ごとに「正解／要確認／誤り」。正解が空欄なのに値を読んだ欄は「誤り」に足す。1枚1タンクの用紙は、タンク番号も1欄として数える。
- 見出しの対応は、Claude の推定をそのまま使った（人の確認なし）。「確認した見出し」は、Claude が対応に自信がなく、取り込み画面で蔵人に確認する見出し。

- 写真（ふつう・悪条件）・PDF・Excel は、6書式とも 1回目・2回目とも全欄正解。見出しの対応の誤りも 0。
- 「温度」（品温か室温か）と「BMD」（多くの蔵では「ボーメ×醪日数」の別の値）は、Claude が決めつけずに確認に回した。取り込み画面ではここで「この列は品温ですか？」と聞き、答えを書式として覚える。
- 限界の写真では、読めない欄の多くを推測で埋めず「要確認」にした（350欄のうち 22欄）。誤りは 1欄（下の「残っている誤り」）。

## 正解率の低かったもの（4）と直したこと

限界の写真を加えた1回目：

| 書式 | 限界の写真 | 確認した見出し |
|---|---|---|
| 標準（用紙どおり・日付が横） | 92.5%（62/67・要確認5） | なし |
| 日付が縦に並ぶ | 86.4%（51/59・要確認8） | なし |
| 項目名が違う（BMD・SMV・アル分 など） | 90.9%（50/55・要確認5） | 温度、BMD |
| 項目の順番が違う | 96.8%（61/63・要確認2） | なし |
| 一部の項目が無い | 91.2%（31/34・要確認2・誤り1） | なし |
| 複数のタンクを1枚に | 94.4%（68/72・要確認4） | なし |
| **合計** | **92.3%**（323/350・要確認26・誤り1） | |

1. **タンク番号の読み違い（誤り）**：「一部の項目が無い」の用紙で、手書きの「8」を「5」と読み、自信ありとしていた。記録が別のタンクに入ってしまう、いちばん困る誤り。
   - 原因：用紙全体のタンク番号は自信の印がなく、読み直しも、人の確認もされていなかった。
   - 直したこと：(1) タンク番号にも自信の印を付け、自信がなければ拡大して読み直す。(2) 読んだ日付と日順を、蔵にすでにある記録と突き合わせる（仕込みの始まりがタンクごとにずれているので、同じ日付の日順でタンクが決まる）。合わなければタンクを「要確認」にし、「日順から見ると8号の記録と合います」と合うタンクを示す。プログラムの決まった計算で、醸造の判断ではない。
   - 2回目：同じ用紙でまた「6」と読み違えたが、突き合わせで「要確認」になり、誤りは 0。ただし正しく読めたタンク番号も、自信がない・日順が読めないときは「要確認」になった（4枚）。人が1回選び直すだけなので、誤って別のタンクに入れるよりよいと判断した。
2. **Excel の見出しの書き写しの揺れ**：同じ Excel でも、Claude が書き写した見出しが回によって少し違い、覚えた書式に当たらないことがあった（3の確認の画面で見つけた）。見出しは Claude の書き写しでなくセルの文字そのものを使うように直した。
3. **「12.5℃」が数値にならない**：文字をそろえると ℃ が「°C」になり、C が残っていた。単位の外し方を直した（テストで見つけた）。

### 残っている誤り（まだ測り直していない直し）

- 限界の写真の「標準」で、備考の「切れ鈍い」を「切れ良い」と読んだ（意味が逆）。文字の欄は、1字でも迷えば言いそうな言葉で補わず「要確認」にするよう、読み取りと読み直しの指示を直した。
- 読み直し（1つの欄の拡大）が 30秒の時間切れになることがあったので、考える深さを「中」に下げた。
- タンク番号の突き合わせで、日順そのものが「要確認」の日は使わないようにした（正しいタンク番号を疑わないため）。
- この3つは、Claude API の利用額の上限に達したため、まだ測り直していない。上限が見直されたら、限界の写真だけ測り直す（`run.html?media=extreme`）。

## 限界

- 手書きは手書き風の書体で描いたもので、本物の手書き（字のくせ、書き直し、にじみ）より読みやすい。本物の手書きの経過簿では、正解率はこれより下がるはず。読めない欄は推測で埋めず「要確認」にする作りなので、誤りより要確認が増える方向に働く。

## 測り直し方

1. `npm run dev`（netlify dev。`web/.env` の APIキーを使う）
2. 用紙をつくる：`http://localhost:8888/eval/make-sheets.html`（`?save=1` で保存の受け口へ送る）
3. 読み取って比べる：`http://localhost:8888/eval/run.html?media=photo,hard,extreme,pdf,excel&save=1&out=results.json`（30通りで Opus を 70回ほど呼ぶ。利用額に注意）
4. 表にする：`node eval/report.mjs eval/results-*.json`

`eval/` は開発中だけ使うページで、本番（Netlify）には載せない。
